旧来の遅い実装ではなく、直前コミット `e25dadf` を比較基準にします。
実測値・9回分の生データは `results.json` を参照してください。

|---|---:|---:|---:|

| 穴・扉補完デモ | 0.680 | 0.602 | 1.130 |
| 人工110部屋 | 62.125 | 46.304 | 1.342 |
| 人工550部屋 | 401.040 | 318.248 | 1.260 |

比較した浮動小数点値は1,123,456項目で、差分は0です。キャッシュなしの直接計算は
110部屋で1.377倍、550部屋で1.312倍でした。warmは約0.940〜1.111倍で、
110部屋は9.064→9.637 msと約6%悪化しています。warm経路の換算処理は変更しておらず、
この測定では一律の改善を主張できません。速度は同一プロセス内の9回の中央値であり、
マシン負荷・メモリ回収の変動を含みます。

## 論文の調査と採用判断

- [Leutenegger et al., STR: A Simple and Efficient Algorithm for R-Tree Packing (1997)](https://www.cs.odu.edu/~mln/ltrs-pdfs/icase-1997-14.pdf)
  は空間領域をまとめて格納して検索候補を絞る手法です。本アプリは既にSTRtreeを採用済みなので、これを新規導入による成果とは数えません。
- [Boncz et al., MonetDB/X100: Hyper-Pipelining Query Execution (CIDR 2005)](https://www.cidrdb.org/cidr2005/papers/P19.pdf)
  のベクトル単位処理を参考に、辺ごとの検索呼び出しを部屋の輪郭単位にまとめました。DB用の論文の速度倍率をこのアプリに当てはめるものではありません。
- [Amdahl, Validity of the Single Processor Approach to Achieving Large Scale Computing Capabilities (1967)](https://www.cs.cmu.edu/~18742/papers/Amdahl1967.pdf)
  の議論に従い、幾何判定以外の処理時間も含めて評価します。特定の検索関数だけ100倍でも、解析全体が100倍になるとは限りません。

## 実装

1. STRtree の検索矩形作成・検索をバッチ化。検索枠の計算式は維持し、候補を元の線分順にソートしてから従来の射影判定に渡します。64辺を超える輪郭は候補保持量を抑えるため逐次検索を維持します。
2. 穴のない部屋では、検証済みのPolygonを再利用し、同じPolygonの再作成を省きます。
3. キャッシュのJSON書き出しを既存依存の `pydantic_core.to_json` に変更。[公式API資料](https://docs.pydantic.dev/latest/api/pydantic_core/#pydantic_core.to_json)。読み込みは従来の `json.loads` のままです。キャッシュ容量・TTL・結果の変更分離は維持します。

面積・長さ・壁控除の式、浮動小数点演算の順序、丸め方、座標、幾何補正モードは変更しません。

## 一致検証と計測範囲

- 4入力（同梱サンプル、穴・扉補完、サンプルを複製した110部屋／550部屋）×5条件、サンプルの補正モード1条件を、cold/warmの両方で比較。
- 座標を固定seedで微小変形した30入力もcold/warm比較。
- 浮動小数点は許容誤差を使わず `float.hex()` で比較。型、配列順、警告文、ID、全フィールドも比較。
- キャッシュserializerはランダムな浮動小数点ビット列約1万件、負のゼロ・非正規化数・最大有限値の往復もテスト。
- coldはキャッシュクリアを含む解析、warmはキャッシュヒット、uncachedは幾何計算を直接実行。入力検証・HTTP・応答JSON化・ブラウザ描画は計測対象外です。550部屋は実図面ではなく人工入力です。
- テストした入力で差分ゼロであって、すべての未知の入力での同一性を数学的に証明したものではありません。

## 再現

リポジトリのコミット `e25dadf` の `floorplan-analyzer/backend/app` を別ディレクトリへ展開してから、backendで実行します。

```bash
.venv/bin/python -m benchmarks.exact_speed --reference /path/to/reference/backend/app --output /tmp/exact-speed.json
.venv/bin/python -m pytest -q
```

100倍を狙う次の候補は、処理時間が残る結果オブジェクト生成・検証・シリアライズと幾何判定のネイティブ化です。ただし演算順序やGEOSの結果順序の変更は完全一致を壊すため、別途同じ基準で検証する必要があります。同じ入力の応答をそのままキャッシュする方法は再アクセス専用の改善であり、初回計算100倍とは区別します。
