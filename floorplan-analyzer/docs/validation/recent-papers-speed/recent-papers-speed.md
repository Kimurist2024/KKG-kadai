# 直近半年の論文の考え方による高速化（2026-09-19）

## 目的と前提

- 入力図面の計算を、結果を 1 ビットも変えずに速くする。参考にする論文は、直近半年以内（2026-03-19 以降）に公開されたものに限る。
- 図面の線分は多くても 1,000 本程度と想定する。数百万件を前提にした手法は対象外とし、30〜1,000 本の範囲で効くものだけを採る。
- 正しさは、変更前の実装（`backend/benchmarks/baseline` と変更前のコミット）を正解として、数値のビット・順序・ID・警告まで一致することで確認する。

## 調べた論文と使い方

公開日は、arXiv は各論文ページの投稿履歴（v1）、雑誌論文は Crossref の登録情報で確認した。11 部屋・線分 30 本・約 2ms という規模を直接扱う論文は見つからなかったため、手法そのものではなく、考え方を実測したボトルネックに当てはめている。

| 論文 | 公開日 | 考え方 | このアプリでの扱い |
|---|---|---|---|
| Fleischmann ほか [GeoPandas: Fundamental data structures for vector spatial data in Python](https://doi.org/10.1016/j.compenvurbsys.2026.102495)（Computers, Environment and Urban Systems 130） | 2026-07-21 | コンパイル済みの GEOS を配列単位でまとめて呼び、Python と C の往復を減らす | **採用**。部屋ごとに呼んでいた多角形の作成・妥当性・代表点と、重複領域の座標の取り出しを一括呼び出しにした |
| Pai ほか [Evaluating Learned Spatial Indexes](https://arxiv.org/abs/2606.19034) | 2026-06-17 | 索引は、構築コストを問い合わせの回数で回収できる規模でだけ使う | **設計の根拠**。線分 64 本未満では木を作らない現在の切り替えを、下の実測で確かめた。コードは変えていない |
| Mandarapu, Kunkunuru [The Decode-Work Law: Margin-Governed, Provably-Exact Spatial Joins over Compressed Geometry](https://arxiv.org/abs/2607.01182) | 2026-07-01 | 高価な厳密判定の前に、安い情報で確定できる候補を確定させる。結果は変えない | **試して不採用**。線分ごとの値の事前計算と早期判定を入れたが、同梱データでは差が出ず（2.587→2.568ms）、110 部屋では遅くなった。最適化前を正解にして一致を確かめる検証の形は採り入れた |
| Mahathevan ほか [Splyce: SIMD Vectorization of Sparse Coiteration](https://arxiv.org/abs/2609.19410) | 2026-09-16 | ソート済みの列を走査するループから、データに依存する分岐を減らす | **試して不採用**。区間の併合・切り取りの分岐を減らしたが、純 Python では差が出なかった（1.982→1.992ms） |
| Ehara, Amagata [Duration-constrained Interval Joins](https://arxiv.org/abs/2608.06856) | 2026-08-07 | 短い重なりを、結合の途中で最初から作らない | **実装しない**。壁区間は「併合→短い区間の除去→隙間つき併合」の順で処理しており、短い断片が後段で結合して残ることがある。射影の段階で捨てると結果が変わる |

## 実測 1: どこに時間がかかっているか（変更前、同梱 JSON、中央値）

初回解析 2.28ms の内訳: 辺ごとの処理（50 辺、射影 198 回、区間 72 個）と結果モデルの生成（125 回）が約 1.35ms、部屋どうしの重なりと和集合が 0.45ms、キャッシュへの保存が 0.20ms、部屋の多角形の作成・妥当性・代表点が 0.17ms、キャッシュのキーが 0.06ms。

## 実測 2: 案ごとの効果（同梱 JSON、交互計測、中央値 ms）

|---|---|---:|---:|---|

## 実測 4: 線分 30〜990 本での伸び方

線分を増やした入力は、同梱データ（11 部屋・壁 21 本・ドア 9 本）を x 方向に 1,224px ずつずらして 1〜33 個並べた人工のデータで、実際の図面ではない。

- 確かめられていること: 計算結果の正しさ。各コピーの床面積・壁面積は元の同梱データと一致し（差は 1e-12 m² 以下）、合計は同梱データのちょうど 33 倍になる。変更の前後でも出力は完全に一致する（既定条件・設定変更・`exclude_unset` つきの出力の SHA-256 を比較）。
- 確かめられていること以外: コピーどうしは 200px 離れていて互いに影響しない配置なので、1 つの建物の中に線分が密に並ぶ実際の 1,000 本規模の図面とは、線分の散らばり方が違う。離れたコピーは索引に有利な配置でもある。このため、下の速度の傾向はこの並べたデータについてのもので、実際の図面で成り立つかは別に確かめる必要がある。README には、この節の数値は載せていない。

## 実測 5: 同梱データで、候補検索の方式だけを入れ替えた比較（2026-09-20）

同梱の `sample/sample_mask.json`（壁 21 本・ドア 9 本）だけを使い、候補検索を「外接長方形の走査」と「STRtree を強制」で入れ替えて、キャッシュ無効の直接計算を交互に 101 回測りました。2 つの方式で出力は完全に一致します。スクリプトは `scripts/measure_index_choice.py`、生の値は [index-choice.json](index-choice.json) です。

| 方式 | 中央値 | p95 |
|---|---:|---:|
| 外接長方形の走査（線分 64 本未満の現行の経路） | 1.596 ms | 1.791 ms |
| STRtree を強制 | 1.841 ms | 2.126 ms |

同梱データの規模では、木を作るほうが約 15% 遅くなります。README の 4 章はこの値を使っています。

## 分かったこと

下の 3 項目のうち、線分を増やしたときの速度についての記述（部屋の数にほぼ比例すること、1,000 本で約 0.1 秒、索引による差が最大約 25% であること、現在の切り替えがどの規模でも速いほうに近いこと、64〜150 本で総当たりが約 3% 速いこと、どの規模でも内訳がほぼ同じであること）は、すべて上の並べた人工データでの結果で、実際の図面で成り立つかは別に確かめる必要がある。同梱データそのものについて言えるのは、30 本の行の値、内訳の割合、配列単位の呼び出しで初回解析が 2.32ms から 1.98ms になったことまで。

- 時間は部屋の数にほぼ比例する（1 部屋あたり約 0.2〜0.27ms）。1,000 本でも約 0.1 秒に収まる。
- 索引の選び方で変わるのは、990 本で総当たりに固定した場合の約 25% が最大。現在の切り替えは、どの規模でも速いほうに近い。64〜150 本あたりは総当たりのほうが約 3% 速いが、差が小さいので切り替えの本数は変えていない。
- どの規模でも内訳はほぼ同じ（辺ごとの処理 約 30%、Shapely/GEOS の呼び出し 約 30%、結果モデルの生成 約 15%）。この範囲で効くのは索引の工夫ではなく、部屋・辺ごとの固定費を削ることで、配列単位の呼び出しがそのまま効いた。

## 再現方法

```bash
# floorplan-analyzer/ で実行
backend/.venv/bin/python -m pytest -q test/gpt-6/backend        # 201 件
backend/.venv/bin/python scripts/measure_sample_speed.py 101     # 同梱 JSON、交互 101 回
```

追加したテストは `test/gpt-6/backend/performance/test_cold_batch_exact.py`（一括経路と従来経路の混在、一括作成が失敗したときの警告、無効な外周の順序、`model_fields_set`、API の全応答の一致）。
