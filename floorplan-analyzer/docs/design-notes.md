## 構成の詳細（環境ごとの API の経路・CI）

- `frontend/`：Next.js・React・TypeScript。図面、結果表、計算式、CSVを担当します。
- `backend/app/`：FastAPI。入力検証と幾何計算をここに集めています。
- `test/gpt-6/`：フロント・バックのテスト。`backend/benchmarks/`：性能比較。
- `sample/`：同梱の図面。`docs/`：設計・参考文献・検証記録。
- `infra/terraform/`：AWS構成。`scripts/`：起動・停止ツール。

ブラウザは同一オリジンの `/api/*` に通信します。環境ごとの経路は次のとおりです。

| 環境 | API の経路 | 設定の根拠 |
|---|---|---|
| ローカル | Next.js :5173 → FastAPI :8000 | `scripts/start.sh`、`frontend/src/app/api/[...path]/route.ts` |
| Vercel | Services のルーティング → FastAPI（Next.js のプロキシを通さない） | `vercel.json` |
| Compose | Next.js :3000 → backend:8000 | `compose.yaml` |
| AWS（構成を同梱） | HTTPS ALB → Next.js :3000 → 同じタスクの FastAPI :8000 | `infra/terraform/app/main.tf` |

プロキシの接続先はサーバー側の `API_PROXY_TARGET` で指定します。以前の単一 Function 構成で使っていた `api/index.py` は、互換のために残しているファイルです。現在の Vercel Services 設定は `vercel.json` のルーティングを使います。アプリ直下の `requirements.txt` は `backend/requirements.txt` を参照しています。

主要なAPIは `POST /api/analyze`（multipartの `file`）と `POST /api/analyze/json`（JSONボディ）の2つです。部屋別・全体の集計に加えて、各辺の区間と根拠になる線分のID、警告を返します。ファイル版は不正なJSONを400、容量超過を413で返し、形式や設定の検証エラーは422です。通常画面の条件は固定ですが、API側には条件指定と研究用の幾何補正の設定を残しています。

GitHub Actions には、Pythonとフロントエンドのテスト、本番ビルド、Composeの疎通、Terraformの検証を定義しています。AWSの更新は main を対象にした手動実行で、CIの成功と環境設定が前提です。説明資料しかない今の main では実行できず、コードと workflow を統合してからになります。AWSについては、Terraformの構成の検証（fmt・validate）までを行った記録が [技術構成と検証状況](architecture.md) にあります（2026-09-20 の点検時点では、この環境に Terraform と Docker が入っておらず、再確認はしていません）。

## R-tree による高速化の詳細（図の読み方）


![同じ線分a1・a2・a3を、配置図からR-treeの候補検索、最終判定まで追う流れ](images/rtree-candidate-search-v2.png)

図の読み方：①橙の輪郭の下辺が計算対象の辺で、その周りの破線が検索範囲です。AとBは壁そのものではなく、近くにある線分をまとめた領域を表しています。②木をたどると、領域Bは検索範囲と重ならないので、配下ごと調べる対象から外れます。領域Aは重なるので中を見ますが、a3は自分の外接長方形が検索範囲に入らないため外れ、a1とa2が候補に残ります。③残った候補を角度・距離・射影区間で判定し、平行で近いa1を壁として採用、垂直なa2を角度で除外します。領域が重なることと壁として採用することは別、というのがこの図の要点です。配置や縮尺、木の分岐は説明用の模式図です。

部屋の辺がE本、壁とドアの線分がN本あると、素直に総当たりするとE×N組の比較になります。この組み合わせを減らすために、Shapelyの **STRtree（R-tree系の空間インデックス）** を使いました。

STRtreeは、各線分をx軸・y軸に平行な長方形で囲み、近いものどうしをさらに大きな長方形にまとめて木の形にしたものです。検索範囲が上位の長方形と重ならなければ、その配下の線分は一本も調べずに済みます。遠くにある線分をまとめて候補から外せるのが利点です。

検索の起点は部屋の中心ではなく、いま計算している1本の辺です。その辺の外接長方形を、許容距離の10pxと丸め誤差分だけ上下左右に広げ、x・y両方向で重なる線分を候補にします。ここまでは候補を絞っているだけで、壁として採用するかどうかは、その後に角度・垂直距離・射影区間で判定します。斜めの辺でも手順は同じです。

検索にかかる時間は通常O(log N＋k)（kは候補数）が目安ですが、線分が密集していると候補がほとんど減らないこともあります。木を作る時間や候補を並べ直す時間もかかるので、効果が出るのは線分がある程度多い入力です。そのため、壁とドアがそれぞれ64本未満のときは木を作らずに全件を確認しています。また、候補は元の入力順に並べ直してから処理し、木を使う前と計算の順序が変わらないようにしました。

このほか、同じ入力に対する幾何計算の結果は、最大8件・16MiB・5分間を上限にプロセス内へ保持して使い回します。端点イベント走査も加え、重なった区間や頂点の多い輪郭で起きていた無駄な比較を減らしました。ビームサーチのように候補を上位だけに絞る近似は入れず、絞り込んだ候補はすべて判定しているので、結果は高速化の前と同じです。速度は、何と比べるか・どの入力か・キャッシュが効いているかで変わるので、実測した範囲は冒頭に挙げた検証資料に分けて記録しています。

## 輪郭の基準と注意点の詳細

[図が表示されない場合はこちら](images/room-boundary-wall-reference-v2.png)

![部屋の輪郭が内法・壁芯を通る場合と認識ずれの比較](images/room-boundary-wall-reference-v2.png)

今回は、入力された輪郭が囲む範囲をそのまま部屋の床とみなして計算しています。つまり輪郭を内法（室内側の境界）として、入力のまま扱っています。壁は、向きがほぼ平行で辺から10px以内にある線分をその辺の壁として対応付けます。10pxという幅は、壁線と輪郭のわずかなずれを吸収するために設けた許容距離です。

こう決めたのは、同梱データの輪郭がどの基準で引かれているのか、実際の壁厚がどれくらいなのかがJSONからは分からないためです。上の図はその違いを示した概念図で、輪郭が内法を通っているのか、壁の中心（壁芯）を通っているのかで、本来必要になる処理は変わります。

- **内法の場合**：今回の扱いと一致し、輪郭をそのまま使えます。
- **壁芯の場合**：内法に直すには壁厚が必要です。壁のある辺を室内側へ寄せ、ずれた分だけ角を作り直すことになります。今回の扱いでは、床面積が内法より大きめに出ます。
- **認識ずれの場合**：そもそも輪郭が壁とうまく対応していない可能性があるので、まず対応関係と基準を確かめるところからです。原因を確かめないまま一律に動かすと、かえって誤差が大きくなることがあります。

壁芯から内法への変換と、認識誤差の修正はまったく別の処理です。壁厚が分からないまま推測で輪郭を動かすと誤差の原因が増えるだけなので、輪郭には手を加えずに計算する方針にしました。同梱サンプルではLD＋Kが図面の記載値に近い値になりましたが、比較できたのはこの1例だけなので、輪郭の基準は未確定として扱っています。研究用に用意した補正の実装（方向の正則化）については、[幾何補正の説明](geometry-regularization.md) にあります。

このほかにも、次のような制約があります。

- 共有壁は、隣り合う部屋それぞれの内壁として両面を数えます。控除の対象はドアだけです。
- 小さな隙間を埋める処理を入れているため、実際にある開口まで塞いでしまうことがあります。また、平行な辺が近くに並んでいると、同じ線分が両方の辺に対応してしまう場合があります。
- 自己交差している輪郭、面積が0の輪郭、不正な穴は、警告を出したうえで計算から外します。部屋どうしが重なっている場合も警告しますが、部屋ごとの面積はそのままにして、重複を除いた和集合の面積を併記します。
- 「壁が足りない」という警告や、対応率が20%未満という表示は、目で確かめてほしい箇所の目印として出しています。警告で拾えるのはJSONの中で見つかる不整合までなので、壁面積が0の部屋や警告が出なかった部屋も含めて、最後は図面と照らして確認する使い方を想定しています。

## 輪郭の基準が違うと床面積がどれだけ動くか（同梱データでの試算、2026-09-20 に Codex の点検を受けて書き直し）

同梱データの縮尺では 1px が 1.41cm（1.365m ÷ 96.7px）、壁線の幅 5px が 7.1cm にあたります。README に載せているのは、次の四則演算だけです。

- LD＋K の「壁あり長」は 25.80m（解析結果の LD 19.31m ＋ K 6.49m）。壁のある辺の位置が一律に d だけずれると、面積はおよそ「壁あり長 × d」変わる。
- d ＝ 1px なら 25.80m × 0.0141m ＝ 0.364m²（LD＋K 27.53m² の 1.32%）、2.5px なら 0.91m²（3.31%）。全 11 部屋（壁あり長 76.44m、床面積 48.75m²）では 1px で 1.08m²（2.2%）。
- 図面に記載された LDK は 27.22m² で、入力のままとの差 0.31m² は、この計算で 0.85px 分にあたる。

実際の壁厚も、図面の 27.22m² が内法と壁芯のどちらなのかも分からないので、これは「基準が少しずれると結果がどれだけ動くか」を見るための試算です。頂点から計算し直した面積と JSON の記載値の差は 11 部屋すべてで表示桁では 0 なので、計算の誤差よりも、輪郭がどの基準で引かれているかのほうが結果に大きく効きます。

### 多角形を内側へ寄せる方法を README に使わなかった理由

Shapely の `buffer` に負の値と `join_style=2` を指定して輪郭を内側へ寄せる方法も試しましたが、LD と K の輪郭の扱い方で値が変わるので、README には使っていません。

| 方法（1px 寄せた場合 / 2.5px 寄せた場合） | LD＋K の変化 |
|---|---:|
| LD と K を別々に全周寄せて合計する | -1.68% / -4.19% |
| `unary_union([LD, K])` でつないでから寄せる（2 つの輪郭の間に 2px ほどの隙間が溝として残る） | -1.50% / -3.75% |
| 0.6px 膨らませてつなぎ、0.6px 縮めて隙間を埋めてから寄せる | -1.22% / -3.05% |

LD と K の境界は、3.58m が壁なしで、残りの約 0.93m には壁線 id=31（x≈696、y≈129〜197）があります。2026-09-20 の途中までこの資料に書いていた「LD と K の間には壁が無い」は誤りでした。境界のどこまでを壁として寄せるか、輪郭の間の隙間をどう扱うかで上のように値が変わるため、前提の少ない「壁あり長 × ずれ」の計算だけを README に残しました。`buffer` そのものは、100×50 の長方形で 1 寄せると 4704.0（＝98×48）、2.5 寄せると 4275.0（＝95×45）になることを確かめています。
## Shapely を選んだ理由（ほかのライブラリとの比較、2026-09-20）

このアプリが多角形の処理に使っている機能は、妥当性の検査と理由の説明（`is_valid`・`explain_validity`）、穴つきの多角形、部屋どうしの重なり（`intersects`・`intersection`・`area`）、和集合（`unary_union`）、部屋名を置く代表点（`representative_point`）、線分の空間索引（`STRtree`）、配列単位の呼び出し（`polygons`・`linearrings`・`get_coordinates` など）です。使用しているのは Shapely 2.0.7（GEOS 3.11.4 を同梱、パッケージ約 4MB）で、`pip install` だけで入ります。

| 観点 | Shapely（GEOS） | pyclipper（Clipper） | scikit-geometry（CGAL） | GeoPandas | 自作 |
|---|---|---|---|---|---|
| 座標の扱い | 倍精度のまま | 整数に直して渡す（倍率を掛けて丸める） | 厳密演算 | Shapely と同じ | 自由 |
| 妥当性の検査と理由の説明 | ある | 別に用意する | ある | Shapely の機能 | 自分で書く |
| 穴・重なり・和集合 | ある | ある | ある | Shapely の機能 | 境界条件で誤りやすい |
| 代表点・空間索引 | ある | 別に用意する | 一部 | Shapely の機能 | 自分で書く |
| 導入 | pip のみ（GEOS 同梱） | pip のみ | PyPI に配布が無く、conda-forge 版は cgal-cpp・boost-cpp・gmp・mpfr に依存する（2026-09-21 に PyPI の 404 と conda-forge の依存関係を確認） | pandas などが加わる | 依存なし |
| 配列単位の呼び出し | ある（2.0 以降） | 1 件ずつ | 1 件ずつ | ある | — |

入力の座標を変えずに計算し、高速化の前後で結果を完全に一致させる、という条件に合うのは、座標を倍精度のまま扱える Shapely でした。このアプリは、起動スクリプト（`scripts/start.sh`）も Vercel も `requirements.txt` を pip で入れる構成なので、pip だけで入ることも必要でした。壁とドアの区間計算だけは、線分の ID を残すことと演算順序を固定することのために自前の Python で書いています。
