# 開発オーケストレーション

## 目的と役割

UI、幾何計算、Web 調査を分担し、メイン担当が利用者の目的に沿って統合する。アプリはセグメンテーション JSON の解析に加え、画像 AI で輪郭候補を生成する。AI の候補は人による照合・縮尺確認を経て既存の幾何計算へ渡す。応募要件に対応した技術構成は `docs/architecture.md` を参照する。

| 担当 | 主な成果物 | 編集範囲 |
|---|---|---|
| UI | 画面、操作、アクセシビリティ、表示テスト | frontend/src/ の割当ファイル。types.ts・api.ts を除く |
| アルゴリズム | 幾何計算、入力検証、API スキーマ、pytest | backend/ の割当ファイル |
| Web リサーチ | 判断に必要な比較、出典、未確認事項 | 読み取り専用。報告はメイン担当へ返す |
| メイン担当 | 要件、API 同期、統合検証、結果報告 | 共通ファイル、types.ts、api.ts、docs、設定。必要な未割当作業 |

役割は編集方針であり、OS のアクセス制限ではない。共通ファイルの担当を変更する場合は、元の担当を止めてから引き継ぐ。

## 進め方

1. メイン担当が依頼を具体的な受入条件に変換する。精度改善なら評価対象と正解値、UI 改善なら利用者が完了できる操作を定める。
2. 不明な仕様や外部資料が必要な部分だけリサーチを依頼する。調査結果の出典・適用範囲を確認して採否を決める。
3. API 変更時はフィールド名、型、単位、null の扱い、警告コード、レスポンス例を先に合意する。backend 実装後にメイン担当が types.ts・api.ts を同期し、それから依存する UI 作業を開始する。
4. 依存関係がなく編集ファイルが重ならない作業だけ並列化する。3 担当を毎回起動する必要はない。完了した作業に追加の変更が必要な場合も担当を明示する。
5. メイン担当が変更内容と検証出力を読み、UI → API → 計算結果 → 表示・CSV の一連の動作を必要な範囲で確認する。不具合は該当担当へ再現条件付きで戻す。
6. 受入条件を満たし、必要な検証が成功したら完了。未実施・既存不具合・残る精度の限界は分けて報告する。

## 委譲テンプレート

```text
担当:
目的・利用者の困りごと:
読むファイル・前提・API 契約:
編集してよいファイル（他の担当との重複なし）:
今回の対象外:
受入条件:
必要な検証:
終了条件・調査範囲:
返すもの: 変更ファイル、変更理由、検証結果、残る問題、他担当への依頼
```

報告は推測と実測を区別する。コードを書いたことだけで完了にせず、実行したコマンド・結果・未実施理由を添える。メイン担当は必要に応じて反証や再現条件を確認する。

## 検証

以下はワークスペース直下（このアプリの親ディレクトリ）から実行する。実行前に作業ディレクトリを確認する。

```bash
cd floorplan-analyzer/backend && .venv/bin/python -m pytest -q
```

別のシェル、またはワークスペース直下へ戻ってから:

```bash
cd floorplan-analyzer/frontend && npm test && npm run build
```

build は TypeScript の型検査を含む。仮想環境がなければ README の環境構築手順に従い、別環境の pytest に黙って切り替えない。

画面を変更した場合はデスクトップと 375px 幅で主要操作・エラー表示を確認する。縮尺の初回確認、別ファイルへの切替、壁警告、結果と CSV の整合性を維持する。ブラウザを操作できない場合は未確認として記録する。

精度検証では同梱サンプル、外部図面、人手で作った輪郭、人工的な変形テストを区別する。スケールの根拠と正解値を保存し、過去の検証レポートを新しい結果で黙って上書きしない。サンプル期待値を変える必要がある場合は理由と変更前後を明示する。

## 1 サイクルの手順

作業は必ず `work/<話題>` ブランチで行い、`feature/kimura` に PR を出す。**`main` には AI が一切触れない**（反映はユーザーが動作確認してから手動で行う）。

```bash
.claude/scripts/cycle-start.sh <話題>            # feature/kimura の最新から作業ブランチを作る
# … 担当エージェントが codex-task.sh で実装 …
.claude/scripts/verify.sh quick                  # 反復中の確認
.claude/scripts/cycle-finish.sh "<件名>" "<受入条件>"
```

`cycle-finish.sh` は次の順に実行し、途中で失敗したらマージせずに止まる。

1. `verify.sh`（pytest / typecheck / vitest / build）が exit 0
2. コミットして push
3. `feature/kimura` 宛に PR を作成
4. `review.sh` が別コンテキストの Codex に差分をレビューさせ、結果を PR にコメント
5. `VERDICT: OK` なら squash マージしてブランチを削除

### 判定の原則

- **合格判定は exit code だけ**。担当エージェントや Codex の「テストが通りました」という自己申告は受け入れない。報告には実行したコマンドと出力を添えさせる。
- **レビューは正しさと受入条件違反のみ**。スタイルの好みや「念のため」の提案は報告させない。指摘が無ければ無理に作らせない。
- **BLOCK が出たら 2 回まで修正して再実行**。3 回目で通らなければ、履歴を捨てて受入条件から書き直す。
- **ハーネスを足すのは実際に失敗が起きたときだけ**。予防的にルールやスクリプトを増やさない（1 失敗につき 1 行か 1 スクリプト）。

## モデルと実行主体

| 場面 | モデル / 実行主体 |
|---|---|
| 案出し、司令塔、アルゴリズム担当・調査担当の判断・検証・報告 | Claude Opus 5（既定。`.claude/settings.json`） |
| UI（`frontend/src/`）のコード編集 | Claude Fable 5.1（司令塔本人、または `ui-designer`。直接 Edit/Write。ユーザー指定 2026-09-17） |
| backend（`backend/`）のコード作成・変更 | Codex `gpt-6-astra`（`.claude/scripts/codex-task.sh` 経由。effort は high / medium） |
| 差分レビュー | Codex `gpt-6-astra`（`review.sh`。実装者と別モデル・別コンテキスト） |

アルゴリズム担当はファイル編集ツールを持たない。UI 担当は Fable が直接編集し、レビューは Codex が行う。Codex に渡す指示には、編集してよいファイル・対象外・受入条件・検証コマンドを必ず含め、Codex の報告とは別に自分で検証を再実行する。effort は設計判断を伴う変更を high、テスト追加や局所修正を medium とする。

## 利用方法

Claude 向けの担当定義はワークスペースの `.claude/agents/`、共通の入口は `CLAUDE.md`。Codex 向けの入口は `AGENTS.md` で、メイン担当が利用可能な委譲機能に役割本文を渡す。この文書自体がエージェントを起動するわけではない。

依頼例: 「縮尺設定をもっと分かりやすくしたい。必要なら Web リサーチで事例を確認し、UI 担当で実装、メイン担当で統合検証まで進めて」。

Codex の指示ファイルの仕様: [OpenAI 公式 AGENTS.md ガイド](https://learn.chatgpt.com/docs/agent-configuration/agents-md)（確認日: 2026-09-14）。
