# 平面図 面積・壁面積 解析アプリ

公開サイト: https://floorplan-analyzer-taupe.vercel.app （JSON 解析の動作は確認済みです。画像 AI は未設定です）

**部屋・壁・ドアのマスク JSON** をアップロードすると、部屋ごとの **床面積・周長・壁面積** を算出する Web アプリです。
提出用の画面は JSON のアップロードと固定条件での解析に絞り、画像 AI の入力欄は表示していません。

- フロントエンド: TypeScript / React / Next.js App Router（`frontend/`）
- バックエンド: Python / FastAPI（`backend/`）
- AI: FastAPI から OpenAI Responses API を呼び出します（画像入力・Structured Outputs）。キーが未設定でも JSON 解析は利用できます。
- デプロイ: Docker Compose、AWS ECS Fargate 向けの Terraform、GitHub Actions（テスト・ビルド・手動デプロイ）。
- 通信: ブラウザから Next.js の API プロキシを経由して FastAPI へ HTTP でリクエストします。

部屋を選択したときの表示処理の改善と計測結果は [性能検証](docs/selection-performance.md) にまとめています。
面積・壁・扉の計算を高速化した際の、変更前後の全項目比較は [アルゴリズム性能検証](docs/validation/algorithm-performance/report.md) を参照してください。
直前の実装を基準にした最新の高速化、浮動小数点まで完全に一致することの検証、論文調査は [計算結果を変えない高速化](docs/validation/exact-speed/README.md) にあります。100 倍という目標は未達です。
さらに 5 倍の高速化を目指した [端点イベント走査の実測](docs/validation/interval-sweep/README.md) では、人工的な 1,024 頂点の輪郭で初回解析が 7.9〜11.1 倍になりました。ただし同梱図面ではほぼ同じ速度にとどまり、すべての入力で 5 倍という目標は未達です。

課題要件との対応と動作確認の範囲は [技術構成と検証状況](docs/architecture.md)、AWS での手順は [インフラ手順](infra/README.md) を参照してください。

## 1. 起動・操作

Python 3.9 以上と Node.js 20.9 以上が必要です。コマンドは `floorplan-analyzer/` で実行してください。

```bash
./scripts/start.sh   # 起動が完了したら http://localhost:5173 を開く
./scripts/stop.sh    # 停止
```

起動スクリプトは、8000 番と 5173 番のポートを使用中のプロセスを停止したうえで、依存関係のセットアップとサーバーの起動を行います。互いに依存しない処理は並列で実行します。JSON の解析に AI のキーは必要ありません。

1. 初回は同梱のサンプルを表示します。操作方法は画面上部の「はじめての方へ」から確認できます。
2. 手持ちの JSON を選択するかドラッグ＆ドロップすると、固定条件で解析します。
3. 図面または表から部屋を選ぶと、面積・周長と辺ごとの内訳を確認できます。
4. 拡大・ドラッグ・レイヤー切り替えで図面を確認でき、結果は CSV で保存できます。

計算条件は **天井高 2.4m、ドア高 2.0m、96.7px ＝ 1.365m** に固定しています。画面の表示倍率は計算値に影響しません。通常の画面では、画像 AI の入力と幾何補正を無効にしています。

API の疎通確認は `http://127.0.0.1:8000/api/health`、仕様とリクエスト例は `http://127.0.0.1:8000/docs` で確認できます。8000 番にアプリの画面はありません。コンテナで起動する場合は `docker compose up --build` を実行します（画面は 3000 番）。

## 2. 構成と役割

- `frontend/`：Next.js・React・TypeScript。図面の描画、結果表、計算式、CSV 出力を担当します。
- `backend/app/`：FastAPI。入力検証と幾何計算をここに集約しています。
- `test/gpt-6/`：フロントエンドとバックエンドのテスト。`backend/benchmarks/`：性能比較。
- `sample/`：同梱の図面データ。`docs/`：設計・参考文献・検証記録。
- `infra/terraform/`：AWS の構成。`scripts/`：起動・停止ツール。

ブラウザは Next.js の API プロキシを介して FastAPI と通信します。数値はバックエンドで計算し、丸めるのは表示するときだけです。元画像はクライアント側に保持し、解析レスポンスには含めません。座標と区間の計算は純粋な Python、多角形の穴・重複・和集合は Shapely/GEOS、描画は SVG が担当します。

主要な API は `POST /api/analyze`（multipart の `file`）と `POST /api/analyze/json`（JSON ボディ）の 2 つです。部屋別と全体の集計に加えて、各辺の区間、根拠となる線分の ID、警告を返します。不正な JSON は 400、容量超過は 413、入力や設定の不備は 422 で通知します。

それぞれの責務は [ARCHITECTURE](ARCHITECTURE.md)、開発手順は [CONTRIBUTING](CONTRIBUTING.md)、環境変数とデプロイ構成は [技術構成](docs/architecture.md) と [インフラ手順](infra/README.md) を参照してください。

## 3. 面積計算の考え方

### 床面積・周長

入力はまず、部屋（`isLine` が真ではない輪郭）、壁（線分・`label_id=2`）、ドア（線分・`label_id=3`）に分類します。名前のない部屋も計算の対象にします。

床面積は、頂点の外積を順に足し合わせる **シューレースの公式** で求めます。穴の面積は差し引き、周長は外周と各穴の辺の長さを合計します。実寸に換算するときは、長さに `1.365/96.7` を、面積にはその 2 乗を掛けます。JSON に記載された面積はそのまま使わず、頂点座標から計算し直しています。

### 壁面積・ドア控除

部屋の輪郭と壁線は完全には一致しないため、部屋の各辺に壁の線分を投影し、「辺のどの範囲に壁があるか」を区間として求めます。

1. **対応付け**：角度の差が 10° 以内で、壁線の両端が辺の延長線から 10px 以内にあれば、その辺に射影し、辺からはみ出した部分を切り落とします。
2. **壁区間の整理**：重なり合う区間を併合し、極端に短いノイズを取り除いたうえで、小さな隙間と端点のずれを補完します。
3. **開口の特定**：辺全体から壁のある区間を除いた部分を「壁なし」と判定します。
4. **ドア控除**：ドアも 1 枚ずつ射影し、壁と重なる区間だけを控除します。両側の壁の隙間とドアが対応する場合は、壁区間を補完したうえで警告します。
5. **集計**：各辺の結果を部屋ごとに合計します。

`壁面積 = 壁あり長[m] × 2.4m − 控除ドア幅[m] × 2.0m`

式の「× 2.0m」はドアの枚数ではなく高さを表します。ドア上部の 0.4m 分は壁として残ります。採用した線分の ID と区間は保持しているので、図面・表・計算式のいずれからでも根拠をたどれます。ドアをまとめて処理せず、壁との交差を 1 本ずつ取ることで、対応しないドアの ID が混ざるのを防いでいます。

## 4. R-tree による高速化

辺が E 本、壁とドアの線分が N 本あるとき、すべてを突き合わせると E×N 組の比較になります。この組み合わせを減らすために、Shapely の **STRtree（R-tree 系の空間インデックス）** を使います。

各線分を x 軸・y 軸に平行な長方形で囲み、近い長方形どうしをより大きな長方形にまとめて階層構造を作ります。検索範囲と上位の長方形が重ならなければ、その中に含まれる線分を 1 本ずつ調べる必要はありません。遠くにある線分をまとめて除外できる仕組みです。

検索の基準は部屋の中心ではなく、計算対象となる 1 本の辺です。その外接長方形を上下左右に 10px と微小な誤差対策分だけ広げ、x 方向と y 方向の両方で重なる候補を探します。ここで行うのは候補の絞り込みだけで、最終的な対応の判定は角度・垂直距離・射影区間で行います。斜めの辺にも同じ手順を適用します。

検索にかかる時間は通常 O(log N＋k)（k は候補数）が目安ですが、線分が密集した配置ではほぼ全件が候補として残ります。木の構築や候補の並べ替えにも負荷がかかるため、最悪の場合の高速化までは保証しません。壁とドアがそれぞれ 64 本未満のときは木を作らず、全件を確認します。候補は元の入力順に戻してから処理し、計算の順序を変えないようにしています。

同じ入力に対する幾何計算の結果は、最大 8 件・16MiB・5 分間の範囲でプロセス内に保持し、再利用します。さらに端点イベント走査によって、重複する区間や頂点数の多い輪郭で生じる不要な比較を減らしています。ビームサーチのように候補を上位だけに打ち切る近似は使っていません。速度は比較のもとにした実装・入力・キャッシュの条件によって変わるため、実測した範囲は冒頭の検証資料に分けて記録しています。

## 5. 輪郭の基準と限界

![部屋の輪郭が内法・壁芯を通る場合と認識ずれの比較](docs/images/room-boundary-wall-reference.png)

上の図は概念図です。同梱データの輪郭がどの基準で引かれているか、また実際の壁厚がどれだけあるかは分かっていません。

- **内法**：室内側の床面積を求めるだけであれば、原則として壁厚の補正は不要です。
- **壁芯**：内法に変換するには壁厚が必要です。壁のある辺を室内側へ動かし、角を作り直します。
- **認識ずれ**：まず壁との対応と基準を確認します。一律に動かすと、かえって誤差が増えることがあります。

壁芯から内法への変換と、認識誤差の修正は別の問題です。現在の通常画面は入力された輪郭のまま計算し、壁厚による床面積の補正は行いません。対応付けに使う 10px の許容距離も壁厚ではありません。研究用に用意した補正の実装は [幾何補正の説明](docs/geometry-regularization.md) にあります。

そのほかに、次の制約があります。

- 共有壁は部屋ごとの内壁として両面を計上します。窓は控除の対象外です。
- 小さな隙間を補完するため、実際の開口を埋めてしまう可能性があります。また、近接した平行な辺では、同じ線分が両方に対応することがあります。
- 自己交差・面積 0・不正な穴は、警告を出したうえで除外します。部屋どうしの重なりも警告し、部屋別の面積は変えずに和集合の面積を併記します。
- 壁不足の警告や対応率 20% 未満といった指標は、あくまで確認の目安です。壁面積が 0 でないことや警告が出ないことが、実際の図面に対する正しさを保証するわけではありません。

## 6. 検証・AI の活用

同梱データ 11 部屋の合計は **床面積 48.75m²、壁面積 155.54m²** です。LD＋K は 27.52m² で、図面に記載された 27.22m² とは約 1% の差があります。境界の基準の違いや認識ずれが原因として考えられますが、確定はしておらず、数値が近いことだけで精度を保証することはできません。

UI は図面・表・辺番号を連動させ、警告から対象をたどれる構成にしています。ズーム、ドラッグ、CSV 出力、狭い画面での表示、キーボード操作に対応します。計算はサンプル、境界条件、変更前後の比較で検証し、高速化の際も数値・ID・警告・配列の順序が変わっていないことを確認しています。

AI は要件の整理、実装、テスト、別セッションでのレビューに活用しています。採否は課題要件を基準に判断し、実施していない検証を成功扱いにはしません。共通のプロンプトは `.claude/scripts/`、役割の定義は `.claude/agents/`、検討やレビューの記録は `docs/reviews/` に保存しています。

依存関係を導入したあと、リポジトリ直下で次のコマンドを実行して検証します。

```bash
.claude/scripts/verify.sh quick  # pytest・型検査・Vitest
.claude/scripts/verify.sh all    # 上記に加えて本番ビルド
```

通常のコード変更は作業ブランチで検証し、レビューを経て `feature/kimura` に統合します。main への反映はユーザーの明示的な指示で行います。詳細は [開発手順](docs/orchestration.md)、参考文献と追加の検証は [資料一覧](docs/README.md) を参照してください。
