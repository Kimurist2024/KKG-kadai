# 平面図 面積・壁面積 解析アプリ

公開サイト: https://floorplan-analyzer-taupe.vercel.app （JSON 解析を確認済み、画像 AI は未設定）

**部屋・壁・ドアマスク JSON** から、部屋ごとの **床面積・周長・壁面積** を算出する Web アプリです。
提出用の画面は JSON アップロードと固定条件での解析に絞っています。画像 AI の入力欄は表示しません。

- フロントエンド: TypeScript / React / Next.js App Router（`frontend/`）
- バックエンド: Python / FastAPI（`backend/`）
- AI: FastAPI → OpenAI Responses API（画像入力・Structured Outputs）。キー未設定でも JSON 解析は利用できます。
- 配置: Docker Compose、AWS ECS Fargate 用 Terraform、GitHub Actions（テスト・ビルド・手動デプロイ）。
- ブラウザ → Next.js の API プロキシ → FastAPI と HTTP で連携します。

部屋選択時の表示処理の改善と計測結果は [性能検証](docs/selection-performance.md) を参照してください。
面積・壁・扉の計算高速化と変更前後の全項目比較は [アルゴリズム性能検証](docs/validation/algorithm-performance/report.md) を参照してください。

応募要件との対応と動作確認の範囲は [技術構成と検証状況](docs/architecture.md)、AWS の手順は [インフラ手順](infra/README.md) を参照してください。

## 3. 使い方


1. 初回表示で同梱の `sample_mask.json` を自動で読み込み、解析結果を表示します。
   自分の図面は上部の細いファイルバーへ JSON をドロップするか、「別の JSON を選択」から読み込みます。
   URL に `?sample=1`（`&room=1` で部屋 id=1 を選択済み）を付けても自動で読み込まれます。
2. JSON を選ぶと、天井高 **2.4 m**・ドア高 **2.0 m**・縮尺 **96.7 px = 1.365 m** で即座に解析します。入力欄や縮尺確認はありません。幾何補正は無効で、元の座標を使います。
   解析後、平面図の上に部屋（塗り）・壁（赤）・ドア（緑）が重ねて表示され、右側に部屋ごとの表が出ます。
3. **表の行または図面上の部屋をクリック**すると、その部屋がハイライトされ、下部に
   **算出根拠（床面積・周長・壁面積の計算式と、辺ごとの内訳）** が表示されます。
   図面上には辺番号①②…が表示され、内訳表の行と対応します。行にカーソルを合わせると図面上の辺が強調されます。
4. 課題指定の固定条件は画面に常時表示されます。拡大・縮小は表示だけを変え、計算結果には影響しません。
5. 「CSV ダウンロード」で表を Excel で開ける CSV として保存できます。

壁データがない場合、部屋の辺に壁が一切対応しない場合、対応する壁の長さが部屋の周長の 20% 未満の場合は、結果の上部と該当する壁面積に「要確認」を表示します。CSV の「壁面積の注意事項」にも理由を残します。20% は入力の欠落・位置ずれを見つけるための目安で、開放的な空間にも表示されることがあります。警告がないことは精度の保証ではありません。壁データがないときの 0 m² は、実際に壁がないことを確認した値ではありません。

固定条件・即時解析・ファイル切替のフロントエンドテストは `cd frontend && npm test`、壁警告を含むバックエンドテストは `cd backend && pytest` で実行できます。

画像 AI の開閉ボタン・画像選択・利用トークン・送信確認を含む入力欄全体は画面から削除しています。既存の画像認識 API と内部コンポーネントは保持していますが、提出用画面からは利用しません。CSV 出力は引き続き利用できます。

## 4. API 仕様

| メソッド | パス | 説明 |
|---|---|---|
| GET | `/api/health` | 疎通確認 |
| GET | `/api/ai/status` | AI の設定有無（秘密値は返さない） |
| POST | `/api/recognize` | PNG/JPEG から輪郭候補を生成。multipart `file` + `X-AI-Token` 必須 |
| GET | `/api/defaults` | 計算パラメータの既定値 |
| POST | `/api/analyze` | **JSON ファイルをアップロードして解析**（`multipart/form-data`, フィールド名 `file`） |
| POST | `/api/analyze/json` | 同じ解析を `application/json` ボディで実行（他システムからの連携用） |

解析エンドポイントは以下のクエリパラメータを受け付けます（すべて任意）。

| パラメータ | 既定値 | 意味 |
|---|---:|---|
| `ceiling_height_m` | 2.4 | 天井高 [m] |
| `door_height_m` | 2.0 | ドア高さ [m] |
| `scale_px` / `scale_m` | 96.7 / 1.365 | スケール（`scale_px` px = `scale_m` m） |
| `tolerance_px` | 10 | 壁/ドア線分が「辺に沿っている」とみなす許容距離 [px] |

## 5. アルゴリズムの考え方・設計背景

提出用の画面では部屋輪郭の補正を無効にしています。研究用の幾何補正実装と API の任意パラメータは保持していますが、画面からは変更できません。詳細は [docs/geometry-regularization.md](docs/geometry-regularization.md) を参照してください。

### 5-1. 入力の分類

`contours` を次のように分類します。

| 種別 | 条件 | 例 |
|---|---|---|
| 部屋 | `isLine` が真でない多角形 | LD, K, 浴室 … |
| 壁 | `isLine == true` かつ `label_id == 2` | 赤い線分 (2 頂点) |
| ドア | `isLine == true` かつ `label_id == 3` | 緑の線分 (2 頂点) |

`room_name` が `null` の部屋（サンプルでは id=3, 10。図面上のパントリー・シューズクロークに相当）も
面積計算の対象とし、`未命名 #<id>` という表示名を与えたうえで `warnings` で通知します。

### 5-2. 床面積・周長

- **床面積** = 頂点座標にシューレース（Gauss）の公式を適用した面積 [px²] × (m/px)²
- **周長** = 隣接頂点間距離の総和 [px] × (m/px)
- **スケール** m/px = 1.365 / 96.7 ≒ 0.014116

JSON に含まれる `area` / `perimeter` は信用せず、頂点から再計算しています（両者が食い違う場合は
`warnings` に出し、UI でも「JSON 記載値との差」を表示します）。サンプルでは全部屋で一致しました。

### 5-3. 壁面積（本課題の中心）

要件は「壁面積 = 辺の長さ × 天井高、ドア部分は控除、**壁が存在しない輪郭区間がある**」です。
部屋の輪郭の辺と壁線分は別々の輪郭として与えられ、座標も数 px ずれているため、
**「各辺のうち、どの範囲に壁があるか」を 1 次元の区間として求める** 方針を採りました。

部屋の各辺 `A→B`（長さ L）について:

1. **射影**: 各壁線分 `P–Q` について、(a) 辺とのなす角が 10° 以内（平行性）、かつ
   (b) 両端点から辺を含む直線までの垂直距離が **`tolerance_px`（既定 10 px ≒ 14 cm）以内**（近接性）
   なら「この辺に沿う壁」と判定します。辺に直交して突き当たる壁（T 字接合）や、許容帯の中を斜めに
   横切る短い線分は除外されます。採用した壁は辺上の位置 t（A からの距離）に射影し、`[0, L]` にクリップして区間にします。
   1 本の長い壁（例: 建物外周の壁）が複数の部屋の辺にまたがっていても、クリップにより各部屋に正しく配分されます。
2. **ノイズ除去**: 重なる区間を併合したうえで、`min(tolerance_px, 辺長/2)` 未満の極短区間を捨てる
   （直交する壁の端がわずかに重なった部分など）。上限を辺長の半分にしているのは、輪郭の辺が細かく分割された
   データでも辺を覆う壁を捨てないためです。補完（次の 3, 4）より先に行い、ノイズが補完で膨らむのを防ぎます。
3. **隙間併合**: `tolerance_px` 以下の隙間を併合（セグメンテーションで分断された壁を 1 つの壁として扱う）。
   したがって **`tolerance_px` より短い開口は検出しません**（意図した仕様。5-5 参照）。
4. **端点スナップ**: 辺の端から `tolerance_px` 以内まで届いている区間は端まで延ばす
   （壁の端点と部屋の角の座標が 1〜3 px ずれるセグメンテーション誤差の吸収）。
5. **開口区間** = `[0, L]` − 壁あり区間。ここが「壁が存在しない輪郭区間」で、壁面積に含めません。
6. **ドア**: ドア線分も同様に辺へ射影し、**ドアごとに** 壁あり区間との共通部分を取ってから併合し、控除対象にします
   （壁のない所にドアがあっても控除しない。該当ドアは `warnings` に出す）。
   扉部分で壁線が途切れる入力も扱います。扉線が両側の壁で挟まれた隙間に対応する場合だけ
   壁区間を補完し、警告と紫点線で明示します。連続した壁の入力も従来どおり扱います。
7. **辺の壁面積** = 壁あり長 [m] × 天井高 − ドア長 [m] × ドア高
   （ドア上部の垂れ壁 0.4 m 分は壁として残る、という要件どおりの解釈）。
8. **部屋の壁面積** = 全辺の合計。

すべての中間結果（区間の位置・長さ・寄与した壁/ドアの id）を API レスポンスに含め、UI で根拠として提示します。

### 5-5. 許容誤差 `tolerance_px` について

サンプルでは壁線分と部屋輪郭のずれは最大でも 2〜3 px（壁の `lineWidth` 5 px の半分程度）でした。
既定値 10 px（≒ 14 cm）はこれを十分吸収しつつ、隣接する平行な壁（最短でも数十 px 離れる）を誤って
拾わない値として選びました。提出用の画面ではこの値も固定です。

## 6. UI 設計において工夫した点

> UI は実装後、GPT 6 (OpenAI Codex CLI) と Claude が 4 ラウンド対話しながら改善しました。
> 提案・採否の判断・実装内容・最終判定の全文は `docs/reviews/ui_dialogue.md` にあります。

- **結論から読める算出根拠**: 部屋を選ぶと、まず「壁面積（ドア控除後）＝ 壁部分 − ドア控除」の分解式を
  大きく表示し、その下に床面積（px² × スケール²）・周長の計算式、辺ごとの「壁あり／壁なし／ドア」の内訳を
  並べます。座標・線分 id・JSON 記載値との差は「元データとの照合」に折り畳み、必要なときだけ開けます。
  内訳のチップはホバーで一時強調、クリックで確定選択でき、対応する壁・ドア線分が図面上で強調されます。
- **表 ⇄ 図面 ⇄ 詳細の往復が 1 タップ**: 表の行や図面の部屋をクリックすると相互にハイライトされ、
  図面直下の選択バーと表の選択行に「算出根拠を見る」、詳細側に「図面で確認」を置いて往復できます。
  辺番号はクリックで選択が保持され（ホバーとは別）、「選択部屋に合わせる」で図面をその部屋に寄せられます。
- **壁なし区間の可視化**: 選択した部屋の輪郭に、壁あり区間（濃赤の実線）・壁なし区間（橙の点線）・
  ドア（緑）を描き分け、辺番号①②…を図面と内訳表の両方に表示して対応付けています。
  表でも「開口」列が 0 でない部屋は色付きで表示し、壁が欠けている部屋に気付けるようにしました。
- **課題条件の可視化**: 天井高・ドア高・スケールを固定値として常に表示します。
  入力や確認の手間を省き、JSON 選択後すぐに解析します。完了時は「結果を更新しました」を通知します。
- **データ品質の通知と誘導**: `room_name` がない部屋、壁に対応付かなかったドア、JSON 記載面積との不一致などを
  種類別に要約して表示し、「対象を確認」で該当の部屋・線分へ移動できます。名前のない部屋には UI 上で
  表示名を付けられます（元の JSON は変更せず、表示と CSV にのみ反映）。
- **壁面積の定義を隠さない**: 列名を「壁面積 (ドア控除後)」「壁なし長」「控除ドア幅」とし、合計の直下に
  「内壁面積の合計・共有壁は両面計上・窓は控除対象外」を常時表示しています。
- **実務での利用を想定した補助機能**: 列見出しで並べ替え、CSV ダウンロード、レイヤーの表示切替
  （元画像／部屋／壁／ドア／部屋名）、ズーム（全体／選択部屋／＋−）、Esc で選択解除、
  `?sample=1&room=1` 形式の共有 URL、ドラッグ＆ドロップ対応。
- **スマホ・キーボード・スクリーンリーダー**: 狭い画面では表を「部屋／床面積／壁面積」の 3 列に絞り
  「全項目を表示」で切替。辺番号やボタンは画面上のピクセル基準でタップしやすい大きさにし、表の行・辺・
  チップは Tab と Enter で操作できます。状態変化は `role="status"` / `role="alert"` で通知します。
- **すぐ試せる**: 「サンプルデータで試す」ボタンで、ファイルを用意しなくても動作を確認できます。

## 7. フロントエンド / バックエンドの責務分担・API 設計の判断と理由

| 責務 | 担当 | 理由 |
|---|---|---|
| JSON の構造検証、面積・周長・壁面積の **計算** | バックエンド | 数値の正しさを 1 か所で保証し、単体テストで担保する。他のクライアント（バッチ処理・別 UI）からも同じ結果を得られる。 |
| 計算式の文字列化、単位表示、並べ替え、CSV | フロントエンド | 表示の都合であり、計算結果（数値）から導出できる。 |
| 元画像 (base64) の表示 | フロントエンド | ユーザーが選んだファイル内にすでにあるため、**API レスポンスには画像を含めず** 往復のデータ量を抑える（画像は 340 KB）。 |

設計上の判断:

- **フレームワーク**: バックエンドは FastAPI（pydantic による入力検証と OpenAPI 自動生成が課題の
  「データ構造」定義とよく合う。軽量で依存が少ない）。フロントエンドは Next.js + React + TypeScript
  （API の型を `types.ts` に写して型安全に扱う。ビルドが速く、可視化は SVG で十分なため描画ライブラリは不使用）。
- **幾何計算**: 線分の射影・区間処理は Python、多角形の穴の検証・交差・和集合は Shapely/GEOS を利用します。
  床面積にメッシュ近似は使いません。領域の仕様と検証は [領域の拡張](docs/geometry-upgrade.md) を参照してください。
- **API は事前状態なしで利用可能**: ファイルを保存せず、1 リクエストで解析結果を返します。パラメータ
  （天井高など）はクエリで渡し、既定値はサーバー側 (`/api/defaults`) が持ちます。
  同じ輪郭・許容誤差の幾何結果だけをプロセス内メモリで最大8件・JSON合計16MiB・5分間再利用します。
  縮尺・天井高・扉高の変更では換算と集計をやり直し、画像本体はキャッシュしません。
  別インスタンスへのリクエストや期限切れでは通常の幾何計算を行います。キャッシュは永続ストレージではありません。
- **アップロードは `multipart/form-data`**（要件の「ファイルをアップロード」に素直に対応）。あわせて
  `application/json` ボディ版 (`/api/analyze/json`) も用意し、プログラムからの利用にも対応しました。
- **根拠データを API に含める**: 「辺ごとの区間」まで返すことで、UI が説明責任を果たせる。
  数値の丸めは行わず、表示桁数はフロントエンドが決めます。
- **エラーは HTTP ステータスで区別**（400: JSON 不正、422: スキーマ/パラメータ不正、413: サイズ超過）し、
  フロントエンドはメッセージをそのまま表示します。

## 8. 前提・制限事項と今後の拡張

> **コードレビューの記録**: 実装後、OpenAI Codex CLI（モデル gpt-6-astra）による第三者レビューを 2 回実施し、
> 指摘のうち妥当なもの（斜め線分の誤採用、ドア id の混入、NaN 入力、読み込みの競合、CSV の数式注入、
> 細分化された辺での壁の消失、アクセシビリティなど）を修正しました。レビュー原文は `docs/reviews/review_gpt6_codex.md`
> （第 1 回）、`docs/reviews/review_gpt6_codex_2.md`（第 2 回）、`docs/reviews/review_gpt6_codex_3.md`（最終確認）にあります。

- **壁は両面計上**: 2 部屋に挟まれた壁は、それぞれの部屋の内壁面積として両方に計上します
  （部屋ごとの内装面積を求める前提）。建物全体の壁面積を求める場合は共有壁の扱いを別途定義する必要があります。
- **壁の厚み・柱型・開口の高さ差は考慮しない**: 課題の定義どおり、辺の長さ × 天井高で計算します。
  窓などドア以外の開口は入力に無いため控除しません。
- **扉補完は条件付き**: 両側の壁との対応を確認できる隙間だけ補完し、扉上部の垂れ壁を計上します。
  孤立した扉や壁端と整合しない扉は補完しません。
- **`tolerance_px` より細い部屋・近接した平行辺は想定外**: 同じ部屋の向かい合う辺が `tolerance_px` 以内に
  近づくと、1 本の壁が両方の辺に採用されます（実在する部屋の幅では起きません）。
- **不正な形状の扱い**: 面積0・自己交差・不正な穴のある部屋は警告付きで集計から除外します。
  重複idや3頂点以上の線分も警告します。
- **入力検証**: 座標・パラメータの NaN/無限大、ドア高 > 天井高は 422 で拒否します。
- **穴と重複**: `holes` は頂点配列の配列として受け付け、穴を床面積から除外します。周長は内周を含みます。
  部屋の重複は警告と紫斜線で表示し、部屋別の値は変更せず、重複を除いた全体面積を併記します。
- **輪郭は直線多角形を前提**: 曲線の壁は頂点数で近似されている想定です。
- 今後の拡張候補: 壁厚を考慮した壁芯／内法の切替、部屋ごとの天井高（図面の CH 値）の個別指定、
  複数ファイルの一括処理、結果の PDF 出力。

## 9. AI の活用方法と開発ハーネス

本課題は AI の活用が認められているため、生成させること自体より **AI の出力を人が保証できる状態にすること** を先に整えました。

### 9-1. 方針: 規約は「指示」ではなく「ゲート」にする

AI に文章で規約を伝えても遵守は確率的です（テストを実行せずに合格と申告する挙動が知られています）。そこで守らせたい規約を 3 段階に分け、**破られると結果が壊れるものだけを終了コードまで落としました**。

| 段階 | 手段 | 例 |
|---|---|---|
| 弱 | 指示ファイルに 1 行書く | 記述・命名の方針 |
| 中 | プロンプトに機械的に埋め込む | 課題要件、禁止事項 |
| 強 | スクリプトの終了コードで判定 | テスト・型検査・ビルド |

指示ファイルは長いほど個々の指示が無視されるため、弱い段階に載せる量は意図的に絞っています。

### 9-2. 役割分担: 書き手と評価者を分ける

| 役割 | モデル | 担当 |
|---|---|---|
| 司令塔 | Claude Opus 5 | 受入条件の決定、API 契約の調整、統合検証、最終判断 |
| 実装 | OpenAI Codex `gpt-6-astra` | すべてのコード作成・変更 |
| レビュー | 同上（別セッション） | 差分レビュー |
| UI / アルゴリズム担当 | Claude Opus 5 | 仕様とテスト観点の定義、検証。**編集ツールを持たない** |

自分が書いたコードを自分で採点すると、実装時の前提をそのまま正しさの根拠にしてしまいます。そのため担当には編集ツールを与えず、仕様を書いて Codex に実装させ、結果を自分で検証させる形にしました。レビューも実装とは別セッションで行います。役割定義は `.claude/agents/*.md`、入口は `CLAUDE.md`（Claude 向け）と `AGENTS.md`（Codex 向け）です。

### 9-3. 課題要件を常に判断基準にする

課題文（`kadai.md`）は仕様の最終的な根拠なので、Claude 側は `CLAUDE.md` が冒頭で取り込み、Codex 側は委譲用ラッパー `.claude/scripts/codex-task.sh` がプロンプトの先頭に自動挿入します。「読んでから作業せよ」と指示するのではなく、読まない選択肢をなくす形です。`label_id` の意味のように、思い込みで実装すると静かに壊れる箇所に効きます。

### 9-4. 検証ゲート: 合格判定を終了コードだけにする

```bash
.claude/scripts/verify.sh quick   # pytest + 型検査 + Vitest（実装中の反復用）
.claude/scripts/verify.sh         # 上記 + 本番ビルド（完了前の必須ゲート）
```

各検証の成功は結果 1 行だけを表示し、失敗した検証についてのみ出力の末尾 40 行を添えます（検証出力でコンテキストを圧迫し、後続の判断精度を落とさないため）。報告には実行したコマンドと出力を必須とし、「テストは通っています」という自己申告は完了条件として認めていません。

### 9-5. 1 サイクルと PR レビュー

`.claude/scripts/cycle-finish.sh` が次を固定実行し、途中で失敗すればマージせず停止します。

1. `verify.sh` が終了コード 0 → 2. push → 3. 統合ブランチ `feature/kimura` 宛に PR → 4. 別セッションの Codex が差分をレビューし結果を PR にコメント → 5. `VERDICT: OK` なら squash マージ

**`main` への反映は自動化していません。** 手元で動かして問題がないことを確認してから手動で行います。レビュー指示（`.claude/scripts/review.sh`）では報告対象を**正しさの誤りと受入条件への違反に限定**し、スタイルの好みや「念のため」の提案を禁止しました。ギャップを探せと指示されたレビュアは健全な実装にも何かを報告する傾向があり、その全てに対応すると過剰な抽象化を招くためです。

### 9-6. 実測: ハーネスが実際に防いだもの

ハーネス自体を最初のサイクルとして通したところ、レビューが 3 ラウンドで 6 件の欠陥を検出しました。

- **作業ブランチに `main` 宛の PR が既にあると、検証せず再利用して `main` にマージする**（最重要。手動反映の前提を破る）
- 既存ブランチを強制的に基点へ戻し、未マージのコミットを失う
- push 失敗後に再実行すると「変更がありません」で停止し、復旧できない
- レビュー結果を PR に記録できなくても握り潰してマージを続行する

3 ラウンド目には通信障害を仮定した指摘が現れ、9-5 で述べた過剰指摘も実際に観測しました。そこで基準に「通常の利用では起きない仮定の状況だけを根拠にした指摘はしない」を 1 行追加しています。**ハーネスを足すのは実際に失敗が起きたときだけ**とし、予防的にルールやツールを積み増していません。

### 9-7. 使用したプロンプトの所在

プロンプトは使い捨てにせず、再利用される資産としてリポジトリに置いています。

| 内容 | 場所 |
|---|---|

### 9-9. ハーネスで保証できないこと

保証されるのは**テスト・型検査・ビルドの合格と、差分が受入条件に照らしてレビューされたこと**だけです。テストが書かれていない範囲の正しさ（特に壁芯か内法かといった幾何計算の前提）、実ブラウザでの見た目と操作感、AI による輪郭認識の精度は保証されません。これらは 5-4 のサンプル検証、`docs/validation/` の外部図面による検証、および手動確認で補っています。

### 選択部屋への拡大表示

「選択部屋に合わせる」は、部屋を選択してから押すか、先にボタンを押して図面・表から部屋をクリックすると使えます。「全体」で元の表示に戻ります。表示範囲の切替時はスクロール位置をリセットします。

フィット表示は画面の高さ・幅の両方から倍率を決め、部屋全体と24pxの余白を収めます。壁線・破線・ラベル・辺番号は画面上のサイズを基準に描画します。「フィット100%」は枠に収まる表示倍率であり、計算条件の実寸縮尺とは別です。＋で追加拡大し、再度フィットボタンを押すと全体が収まる状態に戻ります。

拡大した図面はマウスの左ボタンでつかんで上下左右へドラッグできます。移動せずクリックすれば部屋・辺を選択できます。下部・右側のスクロールバー、ホイール、タッチスクロールも引き続き利用できます。
